modm-data tools

Answers about STM32 devices for embedded developers and their coding agents: a command line, an MCP server and a few interactive pages.

modm-data converts vendor sources (CMSIS headers, SVD files, the STM32CubeMX database, PDF documentation) into a stable form in the ext/ folder of its checkout. The modm-data tools only read that data. They answer questions like these:

  • Headers: which CMSIS header a device uses, which headers define a macro, which bus a peripheral is on.
  • Registers: the bit fields of a peripheral, and what a value read from a board means.
  • Documents: the datasheet, reference manual and errata of a device; search them, read a section or a table as Markdown.
  • Figures: the labels of a drawing, a PNG of one region, the curves of a chart, the lanes of a timing diagram.
  • Clocks: the clock tree, flash wait states, and a clock configuration for frequency targets with the modm SystemClock code.
  • Interrupts: which events share a vector, with their enable, flag and clear bits, and the trigger multiplexers between peripherals.
  • Pins: the alternate functions of the device pins and the connector pins of NUCLEO boards and Discovery kits.

The same 25 lookups are available as the modm-data-lookup command and as MCP tools. Every lookup takes text and returns text.

Installation

The tools

You need Python 3.11 or newer, git, and g++ and patch for modm-data. The tools read the data in the ext/ folder of a modm-data checkout, so modm-data is installed from that checkout with pip install -e, not from PyPI. Clone both repositories next to each other:

git clone https://github.com/modm-io/modm-data.git
git clone https://github.com/modm-ext/modm-data-tools.git
cd modm-data-tools
make venv

make venv creates .venv and installs both packages in editable mode:

python3 -m venv .venv
.venv/bin/pip install -e "../modm-data" -e ".[all]"

If modm-data is somewhere else, pass its path: make venv MODM_DATA=/path/to/modm-data. The extra [all] includes the MCP server (mcp, uvicorn) and pytest. This installs two commands into .venv/bin: modm-data-lookup and modm-data-mcp.

The data

All data goes into the ext/ folder of the modm-data checkout. Run these targets there, with the virtual environment of the tools active (source ../modm-data-tools/.venv/bin/activate), since they call python3 -m modm_data….

Public sources

make clone-sources-stmicro       # headers, SVDs, CubeHAL, packs
make convert-stmicro-header-svd  # SVDs from the CMSIS headers

The first target clones the CMSIS headers, the ST SVD files, the CubeHAL drivers, the CMSIS packs of ST and the CMSIS core, all public repositories under BSD-3-Clause and Apache-2.0.

Data you download and convert yourself

The STM32CubeMX database and ST's PDF documentation are under the ST licence agreement (SLA). They cannot be redistributed, so modm-data downloads them from ST for you and you convert them locally:

make download-stmicro-cubemx     # CubeMX database from ST
make build-device-database       # ext/modm-data/devices.db
make download-stmicro-pdfs       # all PDFs, about 10 GB
make convert-stmicro-html        # PDF to HTML, takes long

You can also convert only the documents you need, one PDF at a time:

# converts ext/stmicro/pdf/RM0440-v9.pdf
make ext/stmicro/html-archive/RM0440-v9

The conversion log goes to log/stmicro/html/. The first documentation lookup builds a SQLite full-text index in ext/cache/lookup; it is rebuilt when the HTML archive or the CubeMX checkout moves to another commit. The MCP server starts building it in the background when it starts.

What needs what

DataNeeded by
CMSIS headers, header SVDsSVD Registers and Peripheral Variants pages; together with devices.db: the header and register lookups
devices.db (CubeMX)every lookup that takes a device name: headers, registers, flash latency, pin functions, board pinouts
CubeMX databaseclock trees and the clock solver, the documents of a device (device_docs), interrupts
HTML documentationdocuments, figures, register descriptions, interrupts, interconnect, board pinouts

With the public sources alone you get the SVD Registers and Peripheral Variants pages. The lookups map part names like stm32g474re to headers through devices.db, so even the header and register lookups need the CubeMX database. Documents, figures, clock trees and board pinouts need the ST data as well.

Environment

The defaults work for the layout above. These variables override them:

VariableDefaultMeaning
MODM_DATAthe installed modm-data checkoutthe checkout whose ext/ folder is read
MODM_DOCS_ARCHIVEext/stmicro/html-archiveanother HTML archive, for example a local conversion; it gets an index of its own
MODM_DATA_LOOKUP_CACHEext/cache/lookupthe full-text index and the OCR results

The text of bitmap figures (board photos) comes from the OCR of macOS. On other systems these figures have no text.

Command line

Usage

Every lookup is a subcommand of modm-data-lookup. Activate the virtual environment or call .venv/bin/modm-data-lookup directly. --help lists all of them, and modm-data-lookup <tool> --help shows the full description and the arguments of one:

modm-data-lookup --help
modm-data-lookup doc_section --help
usage: python -m modm_data_tools.lookup doc_section [-h]
                                                    [--subsections | --no-subsections]
                                                    [--offset OFFSET]
                                                    [--max_chars MAX_CHARS]
                                                    doc section

One section as Markdown, with its subsections unless `subsections` is false. Register layouts become one line
per bit field, large tables are only summarized (read them with doc_table). Long sections are paged by `offset`,
`max_chars` is at most 100000.
…

The arguments follow the parameters of the lookup functions:

  • Required parameters are positional arguments: doc_section RM0440 7.2.1.
  • Optional parameters are options with the same name, underscores included: --max_chars 600.
  • Boolean parameters have a pair of flags: --subsections and --no-subsections, --code and --no-code, --image and --no-image.
  • Patterns like find_define's pattern or doc_table's --where are regular expressions. A regex may run for 2 seconds on one text; a slower one is rejected with pattern too slow, simplify it, an invalid one with invalid regex: ….
  • Lists are capped: --limit is at most 200 and --max_chars at most 100000. Larger values are clamped. Long answers say how to get the rest, for example with --offset.

A wrong input prints a message to stderr and exits with 1. Anything else is a bug and prints a traceback.

modm-data-lookup device_header stm99
no STM32 device matches 'stm99', similar: stm32u599vjt6 stm32l4s9ziy6 stm32l4s9zit6 stm32l4s9zij6 stm32l4s9vit6

The examples below are real output, shortened where marked with ….

Headers

A device name is a prefix of the part name, so g474re and stm32g474ret6 both work.

modm-data-lookup device_header g474re
…/ext/stmicro/header/stm32g4xx/Include/stm32g474xx.h (3 devices: stm32g474ret3 stm32g474ret6 stm32g474ret7)

find_define answers which headers define a macro, matched as a full regex:

modm-data-lookup find_define 'FDCAN_CCCR_\w+' --devices g4 --limit 5

Defined in:
all of them: FDCAN_CCCR_ASM FDCAN_CCCR_ASM_Msk FDCAN_CCCR_ASM_Pos FDCAN_CCCR_BRSE FDCAN_CCCR_BRSE_Msk ... (+37)
stm32g411xb.h stm32g411xc.h stm32g414xx.h stm32g431xx.h stm32g441xx.h stm32g471xx.h stm32g473xx.h …

Related: header_devices lists the devices of a header, device_condition writes the lbuild template condition for the devices that define a macro, peripheral_buses lists the bus of every peripheral, and flash_latency the wait states per voltage:

Registers

The registers come from the SVD files generated from the CMSIS headers, plus the Cortex-M core peripherals (SCB, NVIC, SysTick, …) from the CMSIS core headers. register_map shows all registers of a peripheral:

stm32g474xx USART1 @ 0x40013800: Universal Synchronous Asynchronous Receiver Transmitter

0x40013804 +0x004 CR2: USART Control register 2
…

Clocks

The clock lookups work on the clock tree of STM32CubeMX and take its part names, like STM32G474RETx. clock_solve finds a configuration for frequency targets. Targets are exact (40M), relative (49.152M~0.1%), a range (12.288M..12.3M), a bound (ADC<=50M) or max. --config describes the board, --code adds the modm code:

modm-data-lookup clock_solve STM32G474RETx "SYSCLK=max, FDCAN1=40M" --config "HSE=24M" --code
STM32G474RETx: solved in 0.07 s
targets:
  SysCLKOutput = 160 MHz (want max) ok  from SysClkSource < PLLR < PLLN < PLLM < PLLSource < HSEOSC
  FDCAN1 = 40 MHz (want 40 MHz) ok  from FDCANMult < PLLQ < PLLN < PLLM < PLLSource < HSEOSC
clocks: SysCLK 160 MHz, FCLKCortex 160 MHz, AHB 160 MHz, APB1 160 MHz, APB2 160 MHz
power: PWR_Regulator_Voltage_Scale=PWR_REGULATOR_VOLTAGE_SCALE1_BOOST, flash FLASH_LATENCY_4
config: HSEOSC=24M, SysClkSource=PLLCLK, PLLSource=HSE, PLLM=3, PLLN=40, FDCANMult=PLL, PLLQ=8
next: pass this config back with more targets or use items; it keeps these choices where it can.

namespace Board
{
using namespace modm::literals;

/// STM32G474RETx, generated by the clock solver for the modm Rcc API
struct SystemClock
{
	static constexpr uint32_t Hse       = 24_MHz;
	static constexpr uint32_t SysClk    = 160_MHz;
	…
	static constexpr Rcc::PllConfig pll{
		.M = 3,
		.N = 40,
		.R = 2,
		.Q = 8
	};
	…
};
} // namespace Board

Work iteratively: solve the core first, then pass the returned config: line back as --config with more targets. The solver keeps earlier choices where it can. --code needs a modm checkout (see MODM_REPO).

clock_tree shows the tree. With --node it shows the path to a peripheral and the limits, with --config the frequency of every node, the violated limits and the flash wait states:

modm-data-lookup clock_tree STM32G474RETx --node FDCAN1
STM32G474RETx: drawing STM32G4, RCC STM32G4_rcc_v1_0, 80 nodes, 67 peripherals
…
FDCAN1 peripheral <- FDCANoutput
  from: FDCANoutput output <- FDCANMult; FDCANMult mux <- APB1Prescaler* | PLLQ | HSEOSC; APB1Prescaler div 1,2,4,8,16 …
  bus: APB1Output output <- APB1Prescaler [<=170 MHz]

Pins

pin_functions takes a pin, or a regex on signal names to find the pins that can carry a signal:

modm-data-lookup pin_functions stm32g474re --query USART2_TX
stm32g474ret3 (also matches stm32g474ret6 stm32g474ret7)
USART2_TX: PA2 AF7, PA14 AF7, PB3 AF7

board_pinout reads the connector tables of the user manual of a NUCLEO board or Discovery kit. --query takes words that must all match, for example a GPIO to find all its connector pins:

modm-data-lookup board_pinout nucleo-g474re --query PA9
NUCLEO-G474RE: UM2505-v7, device STM32G474RETx
CN5 (arduino):
  CN5-1 D8: PA9, net ARD_D8, function I/O
CN10 (morpho, right):
  CN10-21: PA9

MCP server

The MCP server offers the same lookups as tools to coding agents. All tools are read-only. There are two ways to run it.

Running it

stdio, one server per client: the client starts modm-data-mcp itself. This server has an extra tool, reload_server, which reloads the code of the lookups after you edit them, without reconnecting.

HTTP, one server shared by all clients:

make mcp   # http://127.0.0.1:8765/mcp

This runs uvicorn with --reload, so the server restarts whenever the code of the tools or of modm-data changes. It is stateless, so clients do not notice a restart. Use it when several agents work at the same time: they share one index and one set of caches.

Claude Code

Over stdio, with the absolute path to your checkout:

claude mcp add --scope user modm-data -- /path/to/modm-data-tools/.venv/bin/modm-data-mcp

Over HTTP, with make mcp running:

claude mcp add --scope user --transport http modm-data http://127.0.0.1:8765/mcp

--scope user makes the server available in all your projects. Check it with claude mcp list.

Claude desktop

Add the server to claude_desktop_config.json (Settings → Developer → Edit Config) and restart the app:

{
  "mcpServers": {
    "modm-data": {
      "command": "/path/to/modm-data-tools/.venv/bin/modm-data-mcp"
    }
  }
}

Add "env": {"MODM_DATA": "/path/to/modm-data"} next to command if the tools should read another checkout than the installed one.

Apps

With the environment variable MODM_DATA_MCP_APPS=1 (off by default), decode_register and clock_solve are also MCP Apps: hosts that render apps show the decoded registers drawn like in the reference manual, and the active clock path of the solution with a button for the whole tree (fullscreen where the host has it). The Claude desktop chat and claude.ai render them, Claude Code does not. The model gets the same text either way, the data of the view travels in the _meta of the result. In claude_desktop_config.json:

{
  "mcpServers": {
    "modm-data": {
      "command": "/path/to/modm-data-tools/.venv/bin/modm-data-mcp",
      "env": {"MODM_DATA_MCP_APPS": "1"}
    }
  }
}

The pages are the views of the web pages, bundled into one HTML file each time the host reads them, so edits in web/ show up after reloading the MCP configuration. They load the ext-apps client from unpkg.com and dagre from cdnjs.cloudflare.com, so they need a network connection.

Other clients

Any MCP client works. For stdio, the command is /path/to/modm-data-tools/.venv/bin/modm-data-mcp without arguments. For HTTP, the endpoint is http://127.0.0.1:8765/mcp with the Streamable HTTP transport. The server answers in JSON and refuses the optional GET stream with 405, as the specification allows.

Errors

Errors are tool errors with a message, so the agent can react. A wrong input, like an unknown device, a value out of range or an invalid or too slow regex, returns the message alone:

Error executing tool device_header: no STM32 device matches 'stm99', similar: stm32u599vjt6 stm32l4s9ziy6 …

Anything else is a bug in the tools and the message starts with the exception type, for example KeyError: …. Please report those.

Instructions

The server sends instructions to the agent when it connects. They say which tool answers what, for example:

  • Use device_header, header_devices and find_define instead of grepping modm-data/ext.
  • Find documentation with device_docs, doc_search and find_tables, navigate with doc_toc, read with doc_section and doc_table instead of reading the HTML files.
  • Find figures with doc_figures, read them with doc_figure, and take a PNG of one region when the drawing matters.
  • Solve clocks iteratively: feed the config line of clock_solve back with more targets.
  • Use doc_register for the manual's description, register_map and decode_register for addresses and values read from a board.
  • Over stdio, call reload_server after editing the tools; the HTTP server restarts by itself.

The full text is in src/modm_data_tools/lookup/mcp.py.

Pages

The pages on data.modm.dev run in the browser on data that modm-data generated. They are plain HTML, CSS and JavaScript without a build step. Each page keeps its state in the URL hash, so copy the address to share what you see.

SVD Registers

SVD Registers browses the SVD files generated from the STM32 CMSIS headers, or any SVD file you open or drop on the page. It shows peripherals, registers, bit fields and enumerated values as a table, or the address space as a zoomable map. Filter the file list and the registers with regular expressions, like ^USART\d+$ or CR1\.(RE|TE), optionally in the descriptions too. The hash holds the file name.

Peripheral Variants

Peripheral Variants shows how many different implementations of each STM32 peripheral exist. The register maps of every peripheral instance of every device are merged into variants with a common core and optional features. Compare them by address (binary), by name (source) or with the descriptions aside (similar), and highlight the variants that one device uses. The hash holds the mode, the peripheral group and the variant.

Board Pinouts

Board Pinouts shows the connector pins of the NUCLEO boards and Discovery kits with their alternate functions, grouped into sets of boards that are compatible on those pins. Search pins, functions, board uses and solder bridges by regex, like ^SPI\d_SCK$|PA5, show only free or freeable pins, and choose whether compatible means the same name, the same function or only the same position. Hover a pin for its details. The hash holds the filters.

Pin Mapping

Pin Mapping has one page per device with the package drawing and a table of all pins and their signals. Search for a device on the index page. On a device page you assign signals to pins; Copy Share URL puts your assignment into the hash, and you can export and import it as JSON.

Clock Solver

Clock Solver draws the CubeMX clock tree of a device and runs the same solver as clock_solve in the browser (with Pyodide). Set targets on the nodes, lock settings, start from the boot configuration or the maximum performance, and copy the modm Rcc code. The hash holds the whole configuration, and Export and Import save it as JSON.

Serving locally

To use or work on the pages, generate their data in the modm-data checkout and serve the pages on top of it:

make serve   # http://127.0.0.1:8768, data from ../modm-data/docs/src

Pages in web/ take precedence over files in the data folder. python3 serve.py <data folder> [port] serves another folder. In modm-data, make build-homepage generates the data of all pages into docs/src. To generate the data of a single page, run its exporter from the modm-data checkout:

PageData
SVD Registerspython -m modm_data.header2svd.stmicro --all --output docs/src/svd/
Peripheral Variantspython -m modm_data.svd2variants --all --input docs/src/svd/ --output docs/src/variants/
Board Pinoutspython -m modm_data.html2pinout --output docs/src/boards/nucleo.json --pinout docs/src/pinout
Pin Mappingpython -m modm_data.pinout --output docs/src/pinout --templates ../modm-data-tools/templates/pinout
Clock Solverpython -m modm_data.clocks --output docs/src/clocks, then python -m modm_data_tools.clocks --output docs/src/clocks

The second clock step adds the modm Rcc API of every device (from the modm checkout in MODM_REPO) and copies the Python code that the page runs.
